Supply chain

How do I detect npm supply-chain attacks and package poisoning?

Run a free scan of your package.json and lockfile for the three patterns every real npm poisoning incident shares.

package.json + lockfileTyposquat detectionInstall-script auditCLI + Web upload
Short answer: Run webscan run code ./my-project. It flags dependency names one edit away from a popular package (typosquatting), any package — yours or a dependency's — that runs an install script, and any lockfile entry resolved from a non-registry source or missing an integrity hash.

The command

webscan run code ./my-project -f html -o supply-chain-report.html

This is one part of the broader code scan (which also covers SAST patterns, IaC misconfiguration and secrets) — see the secrets scanner page for the rest of it.

The three signals that actually matter

SignalWhy it matters
Typosquatted nameA one-character-off match against a popular package (e.g. react, lodash, express, axios) is the classic bait — this is checked by edit distance, not an exact blocklist.
Install lifecycle scriptsAny dependency with hasInstallScript in the lockfile runs code on install — the real-world delivery mechanism behind incidents like event-stream and the 2024/2025 wave of compromised maintainer accounts.
Non-registry resolutionA lockfile entry resolved from a git/HTTP URL instead of registry.npmjs.org bypasses registry integrity checks entirely.

What to do when it finds something

  1. Verify the package name character-by-character against the one you meant to install.
  2. Audit any flagged install script before running npm install again.
  3. In CI, install with --ignore-scripts and an explicit allow-list for packages that legitimately need them (native addons, etc.).

Frequently asked questions

What is npm typosquatting?
An attacker publishes a malicious package with a name one character off from a popular one (e.g. expres instead of express), hoping a typo in your npm install pulls in their package instead.
What are install scripts and why are they dangerous?
preinstall/install/postinstall scripts in package.json run automatically — with no confirmation — the moment npm install finishes resolving them. They're the single most common delivery mechanism for npm supply-chain attacks, because they execute arbitrary code on your machine or CI runner.
Does this replace <code>npm audit</code>?
No — they're complementary. npm audit (and this tool's own OSV-based dependency scan) checks for known-vulnerable published versions. The supply-chain heuristics in webscan-light additionally catch typosquats, install-script abuse, and non-registry sources that a known-CVE database won't flag because nothing's been disclosed about them yet.
