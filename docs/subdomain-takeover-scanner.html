How do I check for subdomain takeover vulnerabilities?

Run a free scan of your subdomains' DNS records against known-vulnerable cloud-provider fingerprints.

DNS + fingerprint matchMajor cloud providersPassive, non-destructive
Short answer: Run webscan run takeover yourdomain.com. It resolves each subdomain's CNAME, checks whether it points at an unclaimed cloud resource (GitHub Pages, S3, Heroku, Azure, and more), and flags anything exploitable.

The command

webscan run takeover yourdomain.com -f html -o takeover-report.html

Pair it with the Subdomain Finder tool if you don't already have a full list of your subdomains — it discovers them via certificate-transparency logs and DNS brute force first.

A minimal, real example

blog.example.com once pointed at example.github.io via CNAME, hosting a GitHub Pages site. The GitHub Pages project was deleted, but the DNS CNAME was never removed. Today, anyone can create a repository named example.github.io on their own GitHub account and GitHub will happily serve it at blog.example.com — fully impersonating that subdomain.

How to fix a confirmed takeover

  1. Remove the dangling DNS record if the resource is genuinely no longer needed, or
  2. Re-claim the resource (recreate the GitHub Pages repo, re-provision the S3 bucket, etc.) under your own account before anyone else does.

Frequently asked questions

What is a subdomain takeover?
When a DNS record (usually a CNAME) still points at a cloud resource you've deleted — a GitHub Pages site, an S3 bucket, a Heroku app — anyone can claim that resource and serve their own content from your subdomain.
Why is this dangerous?
The attacker's page runs under your domain: it inherits your cookies' scope, can phish with a trusted-looking URL, and can bypass CSP/CORS rules that trust your domain.
Which services are checked?
The scanner matches CNAME targets and response fingerprints against the known-vulnerable patterns for major providers — GitHub Pages, Heroku, AWS S3/CloudFront, Azure, Fastly, Shopify and more.
